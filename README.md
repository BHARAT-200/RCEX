# RCEX

**RCEX (Rathore Chaudhary Encryption)** is a small, lightweight C stream-cipher library inspired by the design of RC4.

The project started as an implementation exercise around a simple stream cipher and was gradually extended with keystream bias reduction, nonce-based initialization, random-byte generation, memory cleanup, and a message authentication mechanism.

The project also includes a collection of statistical and experimental tests used to investigate the behavior of the generated keystream and the effect of changing keys, nonces, and other inputs.

> **Important:** RCEX is a custom cryptographic implementation and has not undergone professional cryptographic review, formal security analysis, or peer review. It should be treated as an educational/research project rather than a replacement for established algorithms such as AES-GCM or ChaCha20-Poly1305.

---

## Features

* RC4-inspired byte-oriented stream cipher
* 256-byte internal S-box
* Key Scheduling Algorithm (KSA)
* XOR-based encryption/decryption
* 5,000-byte initial keystream discard ("whitewash")
* Nonce-based key diversification
* OS-backed random byte generation using `/dev/urandom`
* Basic key/input validation
* Explicit memory wiping for sensitive internal buffers
* 16-byte message authentication tag
* Separate MAC key domain using `"MAC"`
* Tag verification without early exit
* Encryption/decryption using the same stream operation
* Performance benchmarking
* Statistical and cryptographic behavior testing

---

## How RCEX Works

RCEX maintains a 256-byte internal state array:

```c
int8 s[256];
```

The state is initialized using the supplied key through a key scheduling process.

For every keystream byte, RCEX updates two internal indexes and swaps entries in the S-box:

```text
i = (i + 1) mod 256
j = (j + S[i]) mod 256

swap(S[i], S[j])

k = S[(S[i] + S[j]) mod 256]
```

The generated byte is then XORed with the plaintext:

```text
ciphertext = plaintext XOR keystream
```

Since XOR is reversible, the same operation is used for decryption:

```text
plaintext = ciphertext XOR keystream
```

---

## Keystream Whitewashing

RCEX discards the first **5,000 bytes** of generated keystream before normal encryption begins.

This is controlled by:

```c
#define TS 50
#define rcexwhitewash(x, y) \
    for(x = 0; x < (TS * 100); x++) \
        (volatile int8)rcexbyte(y);
```

Therefore:

```text
50 × 100 = 5,000 bytes
```

The purpose is to avoid using the earliest part of the keystream, where stream ciphers can sometimes exhibit stronger initial biases.

The early-keystream behavior was also tested separately as part of the project's statistical testing.

## Nonce Support

RCEX supports nonce-based initialization through:

```c
rcexinit_nonce()
```

The supplied key and nonce are combined before the normal key scheduling process:

```text
combined key = key || nonce
```

The temporary combined buffer is wiped after initialization.

A nonce can be generated using:

```c
rcexrandbytes()
```

which obtains random bytes from the operating system's:

```text
/dev/urandom
```

The nonce does not need to be secret, but it should be unique for a given key when used to generate separate keystreams.

## Basic Usage

Include the header:

```c
#include "rcex.h"
```

### Encryption

A basic encryption flow looks like:

```c
int8 key[] = "my-secret-key";
int16 keysize = sizeof(key) - 1;

int8 plaintext[] = "Hello RCEX!";
int16 size = sizeof(plaintext) - 1;

Rcex *ctx = rcexinit(key, keysize);

int8 *ciphertext =
    rcexencrypt(ctx, plaintext, size);
```

The returned ciphertext is dynamically allocated.

When finished with the context:

```c
rcexwipe(ctx);
```

and when finished with the ciphertext:

```c
free(ciphertext);
```

---

## Decryption

RCEX uses the same operation for encryption and decryption.

The header defines:

```c
#define rcexdecrypt(x,y,z) rcexencrypt(x,y,z)
```

So the same function can be used with a correctly initialized context:

```c
int8 *plaintext =
    rcexdecrypt(ctx, ciphertext, size);
```

The encryption and decryption sides must use the same key, nonce, and keystream starting position.

---

## Nonce-Based Encryption

For nonce-based operation:

```c
int8 key[32];
int8 nonce[16];

rcexrandbytes(nonce, 16);

Rcex *ctx =
    rcexinit_nonce(key, 32, nonce, 16);
```

The nonce should be stored/transmitted alongside the ciphertext because the receiver needs the same nonce to reconstruct the keystream.

Conceptually:

```text
             KEY
              │
              │
            NONCE
              │
              ▼
        ┌─────────────┐
        │ key || nonce│
        └──────┬──────┘
               │
               ▼
              KSA
               │
               ▼
       discard 5000 bytes
               │
               ▼
          RCEX keystream
               │
               ▼
      plaintext XOR stream
               │
               ▼
           ciphertext
```

---

## Memory Handling

RCEX includes explicit memory cleanup functions.

For example:

```c
rcexwipe(ctx);
```

clears the internal S-box and indexes before releasing the context.

Temporary buffers used during nonce initialization and MAC generation are also cleared before being freed.

This is intended to reduce the amount of sensitive cryptographic state remaining in memory after use.

It should **not** be interpreted as protection against every type of memory disclosure or side-channel attack.

# Authentication / MAC

RCEX also contains a message authentication mechanism:

```c
rcexmac()
rcexverify()
```

The configured tag length is:

```c
#define MACLEN 16
```

so the generated tag is **16 bytes**.

The MAC uses a separate derived internal key by appending:

```text
MAC
```

to the supplied key:

```text
original key || "MAC"
```

This provides domain separation between the encryption keystream and the MAC keystream.

The MAC is calculated over the supplied data and stored in the 16-byte tag.

Verification recomputes the tag and compares all bytes without returning early:

```c
diff |= (check[x] ^ tag[x]);
```

This avoids the obvious early-exit comparison pattern.

### Important limitation

The current MAC construction is a **custom construction**. It has not been formally analyzed like HMAC, Poly1305, or an AEAD construction.

Therefore, the presence of `rcexmac()` should not be interpreted as making RCEX equivalent to a professionally reviewed authenticated-encryption scheme.

# Testing

A significant part of the project was spent testing RCEX output rather than relying only on successful encryption/decryption.

The tests included statistical randomness testing, keystream bias testing, key-difference experiments, weak-key experiments, and prediction experiments.

The results below are the results obtained during the project's testing.

---

## 1. NIST Statistical Test Suite

### Configuration

```text
Generator: RCEX output
Bitstreams: 100
Bits per stream: 1,000,000
Input format: Binary
```

The NIST STS tests included:

* Frequency
* Block Frequency
* Cumulative Sums
* Runs
* Longest Run of Ones
* Rank
* Discrete Fourier Transform
* Non-overlapping Template Matching
* Overlapping Template Matching
* Universal
* Approximate Entropy
* Random Excursions
* Random Excursions Variant
* Serial
* Linear Complexity

### Observed results

Examples from the generated NIST report:

| Test            |  P-value | Passing sequences |
| --------------- | -------: | ----------------: |
| Frequency       | 0.048716 |           100/100 |
| Block Frequency | 0.401199 |            99/100 |
| Cumulative Sums | 0.122325 |           100/100 |
| Cumulative Sums | 0.699313 |           100/100 |
| Runs            | 0.911413 |            99/100 |
| Longest Run     | 0.304126 |            99/100 |
| Rank            | 0.851383 |           100/100 |
| FFT             | 0.616305 |            98/100 |

The non-overlapping template tests produced varying results, generally between approximately **95/100 and 100/100** in the supplied output.

The NIST output also showed a number of P-values distributed across the expected range rather than all clustering around a single value.

### What this test is for

NIST STS is used to investigate whether generated bitstreams exhibit statistical properties consistent with randomness.

It does **not prove that a cipher is cryptographically secure**. Passing statistical tests only means that the tested output did not exhibit the particular statistical abnormalities those tests are designed to detect.

# 2. Early Keystream Bias Test

### Configuration

```text
Trials: 1,000,000
Positions tested: 256
```

### Observed results

Across the 256 positions:

```text
Lowest chi-square: 194.49
Highest chi-square: 330.26
```

The measured frequency of byte value `0x00` was approximately:

```text
0.3696% – 0.4071%
```

For a perfectly uniform 256-byte distribution, the expected frequency is:

```text
1 / 256 = 0.390625%
```

### What this test is for

This test investigates whether particular byte values occur unusually often at specific positions near the beginning of the keystream.

This matters because early output from stream ciphers can sometimes contain biases related to the secret key.

The test was one of the reasons for introducing the 5,000-byte initial keystream discard.

# 3. Related-Key Avalanche Test

### Configuration

```text
Trials: 100,000
Key size: 32 bytes
Nonce size: 16 bytes
Plaintext: 1024 bytes
```

For each trial, one key was copied and exactly one bit of the key was flipped.

Both versions were then used to encrypt the same plaintext with the same nonce.

### Result

```text
Average changed bits: 50.0003%

Minimum: 47.2290%
Maximum: 52.2095%
```

### Expected

Approximately:

```text
50%
```

### What this test is for

The test investigates how much changing a single key bit affects the resulting ciphertext.

If a small key change produces changes throughout approximately half of the ciphertext bits, it indicates strong diffusion in the particular experiment.

RCEX produced an average of **50.0003%**, which was very close to the expected 50% target.

---

# 4. Differential Test

### Configuration

```text
Trials: 100,000
Key size: 32 bytes
Nonce size: 16 bytes
Plaintext: 1024 bytes
```

### Result

```text
Average changed bits: 0.0122%
Minimum: 0.0122%
Maximum: 0.0122%
```

### Expected

```text
~50%
```

### What this test is for

The purpose of a differential test is to investigate how ciphertext changes when a small input difference is introduced.

For a strong diffusion property, a small input change would ideally affect a large portion of the output.

### Result interpretation

The observed **0.0122%** is far below the expected ~50%.

This is an important result and should not be described as a successful differential test.

It indicates either a significant diffusion weakness under the tested condition or that the particular test implementation is not measuring the intended property correctly.

Further investigation is required before drawing a cryptographic conclusion from this test.

# Security Considerations

RCEX should currently be considered an **experimental cryptographic project**.

It has undergone a number of self-designed experiments and statistical tests, but these do not constitute a formal cryptographic security evaluation.

In particular:

* RCEX is a custom cipher.
* It does not have a formal security proof.
* It has not undergone independent cryptanalysis.
* Statistical randomness does not prove cryptographic security.
* The MAC is a custom construction and should not be treated as equivalent to HMAC or Poly1305.
* The implementation has not been evaluated for all possible side-channel attacks.
* `/dev/urandom` is currently used for random byte generation on Unix-like systems.
* The current API uses `int16` (`unsigned short`) for sizes, which limits the size values accepted by several functions.
* Applications must correctly manage nonce reuse and key management.
* Keys should not be derived directly from human passwords without a proper password-based key derivation function.

For real-world applications requiring strong cryptographic guarantees, use a well-established and independently reviewed construction such as:

```text
AES-GCM
ChaCha20-Poly1305
```

rather than RCEX.

# Current Status

RCEX is a **working experimental stream-cipher library** with additional nonce, memory-handling, authentication, testing, and benchmarking functionality.

The current test results show several encouraging statistical results, including:

```text
Related-key avalanche: 50.0003%
Prediction accuracy:   0.390029%
Benchmark:             690.42 MB/s
```

However, the differential experiment produced:

```text
0.0122% changed bits
```

against an expected approximately 50%, so the implementation and/or test methodology requires further investigation before making stronger claims about RCEX's diffusion or cryptographic security.

This README intentionally reports that result rather than presenting the testing as proof that RCEX is secure.
